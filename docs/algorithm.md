# 자리 배정 알고리즘 — 완전 공개 명세

이 문서는 [ebchange.hyunshu.com](https://ebchange.hyunshu.com)의 자리 배정이 어떻게 동작하는지,
그리고 누구든 결과를 어떻게 검증할 수 있는지 설명한다. 이 문서의 모든 서술은
저장소의 실제 코드(`src/lib/`, `src/app/api/`)와 일치하며, 어긋나면 코드가 정답이다.

## 1. 가중치

학생 s가 좌석 t에 배정될 가중치:

    weight(s, t) = d^n(s, t)

- `d` = 감소 계수 (기본 0.5, 환경 변수 `DECAY_FACTOR`). 유효 범위는 (0, 1].
- `n(s, t)` = s가 t에 앉았던 "배치 기간" 수. 배치 기간 = 셔플부터 다음 셔플까지이며,
  기간 중 자리 교환이 있으면 교환 후 최종 자리 기준. 진행 중인 현재 기간도 1회로
  포함되므로, 지금 앉아 있는 자리는 이미 `n ≥ 1`이다. 무효(invalidated) 세션은
  이력 재생에서 제외된다.
- "직전 자리 피하기(avoidPrev)"가 ON이면 현재 앉아 있는 자리의 가중치만 0으로
  하드 제외된다(`d^n`을 무시하고 0).
- 고정석(`fixedSeatId`) 학생은 추첨 없이 항상 고정석에 앉는다(직전 자리 규칙보다
  우선). 고정석 학생은 가중치 행렬에 행이 만들어지지 않고, 그 자리는 다른 학생의
  추첨 대상(좌석 풀)에서도 빠진다.

구현: `src/lib/weights.ts`(`weight`), `src/lib/history.ts`(`n` 계산),
`src/lib/draw.ts`(고정석 처리).

## 2. 추첨 절차

1. 128비트 난수 시드를 생성한다 (셔플마다 새로, `crypto.getRandomValues`로 16바이트를
   16진수 문자열로 인코딩. 로그의 `seed` 컬럼에 공개).
2. 시드 PRNG(`seedrandom`)로 추첨 대상(고정석 제외) 학생 순서를 Fisher-Yates 셔플한다
   (모든 순열이 균등 확률).
3. 순서대로 각 학생이 남은 좌석 중 가중치 비례로 자리를 하나씩 뽑는다.
4. 어떤 학생 차례에 남은 좌석 가중치가 전부 0이면(막다른 길) 그 시도를 통째로 버리고,
   파생 시드 `시드#1`, `시드#2`…로 처음부터 다시 뽑는다. 재추첨 횟수(`redrawCount`)도
   로그에 기록된다. 재추첨이 `MAX_REDRAWS`(기본 100)회를 넘으면 `DrawImpossibleError`로
   중단한다.

이 절차 전체가 시드에 대해 결정론적이다: **같은 이력 + 같은 옵션 + 같은 시드
→ 항상 같은 결과**.

구현: `src/lib/rng.ts`(시드/셔플/가중 추첨), `src/lib/draw.ts`(전체 절차).

### 2.1 시드 파생 규칙 (전체)

모든 난수는 단 하나의 128비트 루트 시드(`seed`)에서 결정론적으로 파생된다. 따라서
로그에 공개된 루트 시드만 있으면 아래 값들을 전부 재현할 수 있다.

| 용도 | 시드 | 위치 |
| --- | --- | --- |
| 루트 시드 (0회차 추첨) | `seed` | `src/lib/rng.ts` `generateSeed()` |
| 재추첨 k회째 (k ≥ 1) | `` `${seed}#${k}` `` | `src/lib/draw.ts` |
| 몬테카를로 i회째 반복 | `` `${seed}:mc:${i}` `` | `src/lib/montecarlo.ts` |
| 셔플 직전 확률 스냅샷 | `` `${seed}:snapshot` `` (몬테카를로에 전달) → 그 안에서 i회째는 `` `${seed}:snapshot:mc:${i}` `` | `src/app/api/shuffle/route.ts` |

0회차 추첨은 루트 시드를 그대로 쓰고, 재추첨부터 `#1`, `#2`…가 붙는다. 스냅샷은
셔플과 동일한 조건에서 루트 시드로부터 파생되므로, 감사자는 공개된 루트 시드만으로
저장된 확률 스냅샷까지 그대로 재현할 수 있다.

## 3. 표시되는 확률의 의미

화면의 확률은 공식으로 계산한 근사치가 아니라, 위 추첨 절차를 그대로
10,000회(`MC_ITERATIONS`) 시뮬레이션해 얻은 통계다. 즉 **"표시 확률 = 실제 확률"**
(표본 오차 ±1%p 미만). 27명을 27자리에 1:1로 배정하는 문제에서는 각 학생의
확률이 서로 독립일 수 없어서, 정확한 확률은 절차 자체의 통계로만 얻을 수 있다.

셔플을 실행하는 순간의 확률은 스냅샷으로 함께 저장된다(§5). 로그 페이지 등에서
보이는 실시간 조회 확률은 요청 시점에 새로 10,000회 시뮬레이션한 추정치다.

구현: `src/lib/montecarlo.ts`(`estimateProbabilities`),
`src/app/api/probabilities/route.ts`(실시간 조회).

## 4. 검증 방법 (아무나 가능)

1. 로그 페이지에서 세션의 시드, 옵션(직전 자리 피하기 여부), 그 이전까지의 전체
   이력을 확인한다.
2. 이 저장소를 클론한다.
3. 같은 입력으로 아래를 실행한다:

       drawAssignment({ students, seats, history, avoidPrev, decayFactor, seed })

   `tests/statistical.test.ts`의 "재현성 (감사 절차)" 테스트가 그대로 예시다
   (루트 시드 + 옵션 + 이력만으로 배정과 재추첨 횟수까지 재현).
4. 결과가 로그의 배정과 일치하는지 비교한다. 일치하지 않으면 조작이다.

## 5. 조작이 불가능한 이유

- 시드는 배정과 동시에 저장·공개되고, 결과는 시드의 결정론적 함수다.
- 로그는 append-only: 수정·삭제 API가 존재하지 않는다. 세션 스키마의 UPDATE는
  `invalidated` 플래그 한 개뿐이고 DELETE는 없다(`supabase/migrations/001_init.sql`).
  잘못 돌린 세션도 "무효" 표시만 될 뿐 기록은 남고, 무효 세션은 이후 이력 계산에서
  빠진다.
- 확률 스냅샷이 셔플 직전에 함께 저장되므로, 사후에 "확률이 달랐다"고 주장할 수
  없다. 스냅샷 시드도 루트 시드에서 파생(`${seed}:snapshot`)되어 재현 가능하다.
- 코드 전체가 공개되어 있고, 통계 검증 스위트(카이제곱 균등성 검정 포함)가
  저장소에 포함되어 있다: `npm test`로 직접 실행 가능.

## 6. 알려진 한계 (정직성)

- 표시 확률은 몬테카를로 추정치라 ±1%p 미만의 표본 오차가 있다. 셔플 시점의
  스냅샷과 이후 실시간 조회는 서로 다른 몬테카를로 실행이라 소수점 아래가 미세하게
  다를 수 있다(둘 다 같은 절차의 통계라는 사실은 변하지 않는다).
- 가중치는 "자리를 뽑는 시점"에 적용되므로, 학생 순서(균등 셔플)에 따른
  상호작용으로 개별 가중치 비율과 최종 확률 비율이 완전히 같지는 않다.
  그래서 확률을 공식이 아닌 시뮬레이션으로 표시한다.
- 배정은 서버에서 실행되므로, 서버 운영자(사이트 소유자)가 코드를 몰래
  바꾸는 것까지 막을 수는 없다. 대신 시드·이력이 공개되므로 사후 검증으로
  반드시 들통난다.
